# 分则：需求与边界

本页为有效方法；任务先读[通则与索引](../需求理解与验收经验.md)。具体业务规则仍查spec，案例不自动成为新约束。

<a id="r01"></a>

## R01 先独立定义用户结果

**检索词**：擅加条件、收益门槛、工程合理性、默认行为、旧算法。

**适用**：将用户诉求转成实现或验收，尤其是现有程序看似合理时。

**易错**：先接受旧实现，再增加“只有腾人能补别处才留空”等前提；程序与测试共用一个未经确认的假设。

**做法**：按G01列出原话支持的条件与自己的假设；分别写用户期望、相反结果和最小输入，再选实现。效率、成本或现有结构上的建议单独提出；会改变结果的未决项依AGENTS处理。

同类反例还包括：停用发送后是否因“没有替代方式”仍发送，导出全部资料时是否只导出实现者选取的部分，取消操作后是否只恢复已保存值。这些都须回到用户要求的对象与结果核对。

**完成标准**：新增前提不成立而用户条件成立时，结果仍符合原意；每条验收预期都能追溯到用户要求。

**证据**：[E01 留空要求被擅加收益条件](../../history.md#lesson-e01)。后续兼职资源含义已由[E03](../../history.md#lesson-e03)细化，不能把早期解释当成当前业务规则。

<a id="r02"></a>

## R02 从个例提炼通用条件

**检索词**：举例、通用、特例、不只按钮、类似错误、重复发生、姓名、航班号、日期、边界。

**适用**：用户用一个对象或截图说明问题，未明确限定仅处理该例。

**易错**：按示例名称补丁；把按钮、页面或功能名当成原因；只改用户指出的入口；复盘继续围绕原按钮，下一任务无法识别相同错误。

**做法**：按G03写出“触发条件→错误机制→可见结果”，去掉示例名称后仍能解释问题；检索共享数据、转换过程和检查方式的其他入口，逐项处理或说明不受影响的依据。验证至少包含原例、另一个同类入口及一项正常例外；按任务选择边界，不机械套用另一业务的条件。分组问题查[U01](界面与交互.md#u01)，跨流程数据查[D01](数据与配置.md#d01)，无报警漏项查[V04](验证与交付.md#v04)。

**完成标准**：原例从失败变通过，共因的受影响入口逐项有证据或明确未验范围，正常例外保持；教训能用于不同功能，验收不依赖特定姓名、编号或按钮。

**证据**：[E04 不重叠航班误合并的通用修复](../../history.md#lesson-e04)、[E11 重复错误仍被局限到按钮的纠正](../../history.md#lesson-e11)。

<a id="r03"></a>

## R03 纠正理解偏差

**检索词**：你理解错了、之前怎么理解、原意、重申、改需求。

**适用**：用户再次解释同一诉求，或指出实现与原意不同。

**易错**：把原意重申写成需求变更；重复泛泛确认，仍保留自己的隐含前提；解释旧行为后就宣布解决。

**做法**：按G04指出自己解释中多加、少掉或扩大了什么；同步修正当前事实、测试预期和实现，历史保留纠正经过。构造能区分两种理解的例子；确有未知决定时只暂停依赖项，继续独立工作。

**完成标准**：能具体说明偏差、改正位置及用户可见结果；原反例通过，相邻正常情况保留；解释与修复分别标明证据状态。

**证据**：[E02 把同航班专岗扩成跨航班限制](../../history.md#lesson-e02)、[E03 兼职与另占人手的理解纠正](../../history.md#lesson-e03)。
