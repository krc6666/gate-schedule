# 需求理解与验收：防止擅自补条件

这份纪律适用于功能开发、问题排查、配置维护、数据处理和交付，不限于排班。目的在于让实现和证据始终回答用户要的结果，避免解释得通却做偏。

## 开始前：把期望变成可核对的结果

先从用户原话和例子提取四件事：什么情况触发、结果要怎样、适用范围、明确的例外。用户没说的条件标为自己的假设，不能写成已确认事实。

写一个最小的“输入或操作 → 预期结果”例子，再列出相反结果。例如用户要求优先留空，验收就检查指定格是否为空；算法权重看似正确、配置保存成功、其他缺口无法减少，都不能代替这个检查。

完成标准：能指出用户哪句话支持每个影响行为的条件，且测试直接检查用户可见的结果。常规实现细节自行解决，不为已明确的需求反复提问。

还要逐条检查规则的作用范围：针对同一对象的限制不能扩成全局禁止。例如“同一航班内只出现一次”不能推导成“不能去另一个航班”；编辑目录也不能因为某项在一种情境下不合法，就在所有情境中删掉它。验收要成对覆盖“范围内应拒绝”和“范围外应允许”，并把另一个独立优先级造成的结果单独说明。

名称相近的对象也必须逐一核对。例如普通“登机核验”和“登机查验（VIP/F/优先通道）”是两个岗位，不能因为都涉及核验就当作同一个目标。复现须记录用户所指的具体对象、日期和实际生效设置；旧日期、旧保存副本或另一目标的测试通过，只能证明对应范围，不能替代当前截图验收。当前页面未保存、旧入口已关闭时，明确保留证据缺口，不以方便取得的资料代替现场。

界面分组还要核对用户正在比较的尺度。例如底层大件任务共享，并不能独自决定航班列是否合并；用户按航班保障窗口判断分格，验收就同时检查该窗口。把“显示合并条件”和“真实任务身份”分别记录：分格不能悄悄复制任务或拆掉轮换，合并也不能经中间对象传递，把本来不符合条件的首尾对象连在一起。针对所有对象建立通用条件，并覆盖相邻、不相邻、首尾相接、跨日和多对象链式场景，不按示例名称写特例。

现场副本暂不可得时，先主动构造可独立执行的完整业务例子，从实际页面设置一直验证到保存、重排、归档和重新打开，不把反复索要特定截图当成唯一推进方式。设置相反条件作对照，证明测试能发现错误；最小例子通过后，再用整天需求和多人竞争检验。模拟通过与现场修复是两种证据；如果正确设置可成功、已保存设置却指向另一对象，应明确报告这个差异，不为了迎合“肯定有错”去修改已经符合要求的逻辑。

## 容易走偏的四个地方

| 风险 | 必须采取的动作 |
| --- | --- |
| 擅自加“只有……才……” | 检查实现是否新增了触发前提、收益要求、成本门槛或豁免。用户要求成立而新增前提不成立时，结果仍须符合原需求；确需改变行为时先问一个具体例子。 |
| 用工程合理性替代业务目的 | 将“这样更有效率”“撤掉也没用”“本来可以兼任”等判断作为建议提出，不能暗中覆盖用户已确认的结果。 |
| 复述相近，执行条件却不同 | 用能区分两种理解的例子核对；泛泛地问“是不是这个意思”无法确认没有说出的条件。用户笼统确认不能成为Agent后来增补条件的授权。 |
| 测试和原程序观点一致，便宣布正确 | 先用用户例子检查测试的预期值。若新要求在原实现上全部通过，但用户展示的相反结果仍会出现，检查是否只验证了配置、权重或局部函数。 |

举例：要求“停用后不再发送”，不能私加“只有存在替代通知方式才停止”；要求“导出包含当前全部资料”，不能只导出Agent认为有用的资料；要求“取消保留原输入”，不能只保留已保存部分。这些都是把Agent的判断偷偷变成额外业务条件。

用户用改名解释概念时，要检查它是否指出模型遗漏，而不止换文案。例如“接续兼职”说明一人多岗与额外占用一个人是不同事实；不能把“出现两次”直接等同“占两个人手”。先用能区分两者的同一输入成对验收，再追踪优先级的作用对象，不能只复述“某优先级更高”而忽略被比较的对象是否属于该优先级。

## 理解偏差的根因：过早用现有实现解释用户需求

2026-11-20的大件显示问题暴露了这一点：用户按航班保障时段判断两个航班应分格，旧实现却只要发现共用大件任务就合并。Agent原先采用的模型遗漏了显示所依据的航班窗口，测试也沿用“共享任务即可合并”的预期。程序和测试互相印证，仍不能证明用户要的显示结果正确。用户指出MF8683与FD573，只是用一个例子揭示通用条件缺失，并没有把修复范围限定为这两个航班。

这与此前几次偏差有共同原因：先接受现有程序里的判断，再用它解释用户的话，没有先独立写出业务含义和可见结果。具体表现包括给“优先留空”擅加腾人必须有收益的前提，把“同航班专岗”扩大到跨航班，把“同人出现两次”直接视为增加人手，以及把“共用底层任务”直接视为应合并界面。各次问题的对象不同，思考错误相同：把尚未核对的实现假设当成已确认需求。

以后在选实现方案前，必须完成以下检查，答案落到当次计划、事实文档或失败用例中：

1. **先写用户结果。** 明确用户在什么对象、什么范围、用哪个时间或人数尺度判断，最终应看到什么；先不引用现有代码、权重或数据结构作为理由。
2. **拆开容易混同的事实。** 同人出现次数与实际占用人手、单对象限制与跨对象行为、业务任务身份与界面分组、航班窗口与岗位工作窗口分别核对，不凭名称相近或底层关联直接画等号。
3. **提取通用条件。** 用户举例时，提取决定结果的条件；除非用户明确限定，不按具体姓名、航班号或日期写特例。更换示例名称及边界时间后，仍应按相同条件工作。
4. **用能区分两种理解的用例检验。** 专门构造“旧实现的理由成立，但用户要求的结果相反”的输入。例如确实共用任务、航班窗口却不重叠，结果必须分格；再配一个真正重叠且共用任务的合并对照。先证明原程序会失败，再修复完整操作链。
5. **用证据检查自己。** 能解释旧结果为何发生，只说明根因调查有进展；只有用户要求的结果实际出现，才说明修复完成。若测试全部通过、用户的反例仍成立，优先检查自己的理解和测试预期。原意重申不能记成用户改需求，也不把补足理解的负担反复交回用户。

交付前逐项回答：哪些判断来自用户原话，哪些只是自己的假设；用户例子是否已推广为通用条件；有哪些反例能推翻当前理解；用户实际入口是否已出现预期结果。无法回答的项继续调查，不用“算法合理”“原有测试通过”替代。

## 用户指出理解偏差时

先对照用户原话与自己加上的解释，明确承认具体偏差；不要把原意的重申描述成用户改了需求。撤掉错误解释在当前事实文档、测试预期和实现中的影响，历史记录则保留原结论及纠正经过。

以用户最新给出的具体例子建立失败证据，再修复真实操作链。若做过解释性调查，要区分“解释了旧行为为什么发生”与“实现了用户期望”；前者不能作为后者的完成证据。

完成标准：原本违背预期的例子能从失败变成通过，且与原意相邻的正常场景仍成立。若所有剩余步骤依赖一个确实未决的业务选择，保留未完成状态并只问这个选择。

## 交付时：沿实际入口核对

用户从哪里操作，就沿哪里验证，包括保存、重排、归档、新建、恢复、重新打开等后续动作。用户说的是本地程序，就核对原入口实际运行的成品；用户说的是网页，就核对相应网页版本。代码、测试、提交、打包、安装和上线分别记录，不能相互冒充。

完成标准：明确给出用户能看到的变化、实际验证入口和未验证范围。若没有改运行程序，直接说明；用户期望行为改变时，补文档或测试不能单独算交付完成。
